# How each patch is proven to have reached the packaged output.
#
# Applying a patch to the source proves nothing about the package: the file may
# not be in this target's graph, or the build may inline an older copy. So each
# patch leaves a fingerprint that survives minification, and the packaged tree is
# searched for it.
#
# Format, one line per patch in patches/:
#
#   NNNN label|bundle|pattern      the bundle must contain the pattern
#   NNNN label|-|why               no fingerprint is possible; how it is proven instead
#
# Every patch needs a line. A patch with no line fails the check rather than
# passing silently, which is the whole point: an absent line used to be
# indistinguishable from a forgotten one.
#
# Choosing a pattern: match something the patch introduces that minification
# cannot rewrite -- a string literal, an HTML attribute, a comparison against a
# literal. Never a variable name; those are mangled.
#
# Two things the checker now does with these rows, so that neither depends on
# someone remembering:
#
#   * It matches tolerantly. A pattern is written the way one esbuild version
#     happened to emit it -- `case"android"`, `==="/callback"` -- and the next
#     version choosing single quotes or a space would have failed rows describing
#     a tree that is still correct. Quote style and whitespace no longer matter.
#
#   * It requires the pattern to appear in what the patch itself ADDS. The rule
#     here used to read "verify the pattern appears zero times in an unpatched
#     bundle", which is the right rule and was advice to a human, because doing it
#     needs a second full build -- thirty minutes on an arm64 runner. Checking
#     provenance instead is the half that runs offline: a pattern the patch does
#     not introduce cannot be evidence the patch arrived.
#
# That second check is necessary, not sufficient. It catches a pattern lifted from
# surrounding code; it cannot prove the same text appears nowhere else in the
# tree. Proving that still wants an unpatched build, and nothing here does it.
#
# A row proves the patch ARRIVED, not which version of it did, and that used to
# be the trap this file was easiest to fall into. Editing a patch that already
# has a row changes nothing a pattern can see: it still matches, so a published
# server built before the edit passed, the APK was built from it, and the only
# thing describing the new behaviour was a CHANGELOG line.
#
# That half is now covered by something other than a row. build-vscode-oss.sh
# writes vscodroid-patches.json into the tree it produces, recording the sha256
# of each patch's diff, and check-patch-fingerprints.py recomputes those hashes
# from patches/ and compares. A tarball built from different patch text is
# refused wherever that check runs, which includes the fetch and the Gradle
# packaging gate. The prose above each diff is not hashed, because git apply
# never reads it, so rewriting a patch's reasoning there is free.
#
# Everything from the first `diff --git` down IS hashed, comments in the added
# code included. Editing one of those is a rebuild: the published server has to
# be built again and refetched before any APK can be packaged, because until then
# the manifest in the tree names the old text and the gate says so. Budget half
# an hour on an arm64 runner for a comment, and reach for the header when the
# note can live there instead.
#
# Rows are therefore back to answering the question they are good at: did this
# reach the packaged bundle at all. Moving one with a revision is still worth
# doing where the revision introduces something durable of its own -- 0003 is the
# worked example, its pattern moved from `__vsc_disconnect`, which its first
# version already added, to the exit wait a later version added -- but it is no
# longer the only thing standing between an edited patch and a stale server.
